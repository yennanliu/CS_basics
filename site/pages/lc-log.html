LC Log
the only copy

data/progress.txt is the daily practice log, and nothing else in this repo records that a problem was practised. The review plan is compiled from it on every build, so a line written in the wrong shape does not fail — it produces a smaller schedule. /lc-log writes the day in the shape the parser actually reads.

A real run: read the open buckets, sort today into them, write one line, check it round-trips, then say what was guessed.

Why a skill and not a habit

Two shapes that lose data, silently

The log's format is hand-written and forgiving, which is the point — and also the problem. Neither of these produces a warning. Both are already in the file.

▧ A number glued to its label

Each comma-chunk has to start with the digits. others: 678(todo) starts with a letter, so it looks exactly like a named drill and is dropped whole — taking LC 678 with it.

Cost: 93 attempts in the log sit in a chunk shaped like that.

▤ A number after its description

2D LIS (354) is read as LC 2, because the regex takes the first digits it finds. Writing 354(2D LIS) instead records the problem you actually did.

Cost: 16 entries log the wrong problem.

◌ The two readers disagree

suggest_review.py strips bucket labels before parsing; build-review-plan.js does not. So the CLI planner sees those 93 attempts and this site's review plan does not.

Fix: a comma after the label makes both agree.

One pass, no branches

Six steps, in order

The steps never reorder and none of them is optional. Pick one to see what it does and the rule that step exists to enforce.

        they are the entire signal the spaced-repetition schedule runs on.

Arguments are inferred, not interrogated

      
How to call it

      

        Say what you practised, however you would say it out loud. The verdicts are taken from
        your own words.
      

      

        

/lc-log 23 ok, 24 again!!, 25
/lc-log 141 and 142 clean, 128 still fighting me

log today's practice
record that I did the linked list set
update progress

The guardrails

      
What it will not do

      

        This file is a record of what happened. A tool that improves the record is a tool that
        destroys it.
      

      
    
        
  • ×Invent an attempt.Only what you say you practised goes in — not the carried-over todo bucket, and not a problem /lc-python filed in the same session. Filing a solution is not practising it.
    • 
        
  • ×Rewrite a previous day.A problem that went badly on Tuesday still went badly on Tuesday. The log is append-only.
    • 
        
  • ×Flatten or inflate your emphasis.again!! is not again. The bang count is what sorts a chronic problem above an ordinary one.
    • 
        
  • ×Touch PROBLEMS.md's status column.That is /lc-again's job, and a promotion there has to be earned. A practice attempt and a mastery verdict are different records.
    • 
        
  • ×Report done without the round-trip.A misread line produces no error — it produces a smaller schedule. The only check that catches it is reading the numbers back.
    • 
        
  • ×Commit or push unless asked.The practice log gets its own commit. It always has.
    •

The rest of the loop

      
Where it fits

      

        /lc-log is the step after the practice, not after the solving:
        /lc-python and /lc-java file the
        code, /lc-log records the attempt, and /lc-again
        moves the verdict once a problem finally sticks. What it writes is what the
        review plan schedules and what
        suggest review spends its picks on.
