# 資料工程系統設計

> **範圍** —— 資料工程面試的系統設計關：這一關怎麼進行、怎麼評分，資料量的粗估（back-of-the-envelope），資料平台的基本元件，每個設計都依賴的核心觀念，要說出口的取捨，以及八道從需求一路推到故障模式的經典設計題。每個元件背後的機制在各自的深入解析裡，由用到它的那一節連過去。
> **另見**：[`../faq_DE_interview.md`](../faq_DE_interview.md) —— 總覽與考前檢查清單；[`./batch_pipeline.md`](./batch_pipeline.md) 與 [`./stream_pipeline.md`](./stream_pipeline.md) —— 兩份管線深入解析，各有一道完整的設計題；[`./kafka.md`](./kafka.md)、[`./spark.md`](./spark.md)、[`./flink.md`](./flink.md) —— 引擎；[`./data_modeling.md`](./data_modeling.md) 與 [`./schema_design.md`](./schema_design.md) —— 模型與資料表；[`./sql_vs_nosql.md`](./sql_vs_nosql.md) —— 挑選服務層的儲存；[`./aws_service_selection.md`](./aws_service_selection.md) —— 同樣的設計在 AWS 上的做法。

每個答案都先給你會說出口的那句話，再講機制，然後是面試官下一步會追問的取捨。重點不是把每個工具都點名一次，
而是證明圖上的每一個方塊之所以存在，都是因為某個需求把它放在那裡。

## 1) 這一關怎麼進行 ⭐⭐⭐⭐⭐

<!-- abdce5b7be37 -->
### 1-1) 面試官在評什麼

**資料系統設計關評的是：你能否把模糊的需求轉成明確的要求、選出這些要求撐得起來的設計，並在資料遲到、出錯或被重播時為它的正確性辯護
—— 而不是你知道最多工具。**

| 訊號 | 強的回答會展現 | 弱的回答會展現 |
|---|---|---|
| **需求** | 動手畫圖前先問資料量、新鮮度、使用者與正確性 | 第一分鐘就畫出 Kafka → Spark → Snowflake |
| **設計** | 每個元件都能對回一個需求；滿足需求的最簡設計 | 每個方塊都塞一個工具，「因為它能擴展」 |
| **正確性** | 冪等性、遲到資料、去重、回補、schema 變更 | 假設每個事件只到一次、準時、依序 |
| **取捨** | 點出沒選的那個方案，以及什麼條件會讓選擇翻轉 | 只有一個方案，講得好像它是唯一解 |
| **維運** | 監控、資料品質、成本、on-call、重新處理 | 圖畫完就停 |
| **溝通** | 主導整場討論、適時確認、控制時間 | 每一步都等面試官開口 |

後端設計關和資料設計關的差別：後端那關主要在談**服務請求**（延遲、可用性、讀寫路徑）。資料那關主要在談
**隨時間正確地搬運與重塑資料** —— 難題都在重跑、遲到事件、schema 變更，或三週後才發現的 bug 時會發生什麼事。

### 1-3) 會改變設計的釐清問題

**只問答案會改變圖上某個方塊的問題，不會改變的就跳過。** 下表每一列都會翻轉一個真實的決定：

| 問題 | 如果答案是… | …設計就變成 |
|---|---|---|
| 輸出要多新鮮？ | 隔天早上 | 批次、每日分區、最便宜的運算 |
| | 一分鐘內 | 串流引擎、即時 OLAP 或 KV 作為服務層 |
| 誰在用？ | BI 裡的分析師 | 資料倉儲 / lakehouse 表、維度模型 |
| | 每秒 1 萬次查詢的產品 API | 預先算好的結果放在 KV 或快取 |
| | ML 訓練 | 時間點正確（point-in-time）的歷史，而不只是最新值 |
| 數字之後可以被修正嗎？ | 可以 | 以 key 做 upsert 的結果、遲到資料視窗、對帳作業 |
| | 不行（計費、財務） | exactly-once 或先對帳再發布、稽核軌跡 |
| 來源是什麼？ | OLTP 資料庫 | CDC（讀 log），而不是對主庫下 `SELECT` |
| | 手機 / 網頁客戶端 | 擷取 API、客戶端產生的 `event_id`、大量去重 |
| | 第三方檔案 / API | 落地區、schema 驗證、隔離區 |
| 會刪資料嗎 / 有 PII 嗎？ | 會 / 有 | 用讀 log 的 CDC 才看得到刪除；支援列刪除的表格格式；代碼化（tokenisation） |
| 要保留多久歷史？ | 30 天 | 簡單的保留策略，便宜 |
| | 7 年、可稽核 | 不可變的原始層、分層儲存、time travel |

面試官不給數字時，就把假設說出來：*「我先假設每日 1 億活躍使用者、每人 50 個事件 —— 如果差了一個數量級請告訴我。」*

## 2) 資料量粗估 ⭐⭐⭐⭐⭐

<!-- b1f81d4c7767 -->
### 2-1) 該記住的數字

**資料估算只需要四種換算 —— 每天換成每秒、尖峰對平均、原始對壓縮後、吞吐量換成分區數 ——
而且每一個都是數量級，不是 benchmark。**

| 經驗法則 | 數值 | 用來算 |
|---|---|---|
| 一天的秒數 | 86,400 ≈ **10⁵** | 每天 100 萬事件 ≈ 每秒 12 個；每天 10 億 ≈ 每秒 1.2 萬 |
| 尖峰 / 平均 | **2–5 倍**（日夜週期），新品上線或促銷更高 | 擷取與串流作業依尖峰估，批次依總量估 |
| 一個 JSON 事件 | **0.5–1 KB** | 每日位元組 = 每日事件數 × 大小 |
| 欄式壓縮 vs 原始 JSON | **約 3–10 倍**（Parquet + zstd / snappy） | 資料湖每年的儲存量 |
| 規劃用的每個 Kafka partition 吞吐量 | 寫入 **約 5–10 MB/s** | partition 數 = 尖峰 MB/s ÷ 這個值，再依消費端平行度往上取 |
| S3 每個 prefix 的請求速率 | 每秒 3,500 次寫入 / 5,500 次讀取 | 為什麼大量小檔與單一熱門 prefix 會出問題 |
| 目標檔案 / Spark partition 大小 | 檔案 **128 MB – 1 GB**；每個 task 約 128–256 MB | compaction 目標；`shuffle.partitions` 的設定 |
| HyperLogLog | 約 12 KB、誤差約 0.8%，不論基數多大 | 相異計數（§6-4） |

說出數字的出處（*「常見的規劃數字是…」*）。面試官能原諒差兩倍的數字；不能原諒的是估算算完卻從沒變成任何決定。

<!-- c6d4082d81a0 -->
### 3-2) 儲存：依存取模式挑選

**依誰來讀、怎麼讀來挑儲存 —— 大量掃描的分析、單點查詢、低延遲彙總、可重播的事件 —— 而不是依什麼正流行。**

| 儲存 | 存取型態 | 延遲 | 例子 | 不適合 |
|---|---|---|---|---|
| **事件 log** | 依序附加、依 offset 重播 | 毫秒 | Kafka、Kinesis、Pulsar | 臨時查詢、長期歷史（成本） |
| **物件儲存 + 表格格式** | 大量掃描、便宜的永久儲存、`MERGE`、time travel | 秒–分鐘 | S3/GCS + Iceberg / Delta / Hudi | 單點查詢、次秒級 dashboard |
| **雲端資料倉儲** | SQL 分析、join、BI 併發 | 秒 | BigQuery、Snowflake、Redshift | 高 QPS 的產品讀取、大規模串流 upsert |
| **即時 OLAP** | 對新鮮資料做彙總、高併發 | 10–100 毫秒 | Pinot、Druid、ClickHouse | 複雜 join、作為系統的唯一真實來源 |
| **KV / 寬欄式** | 高 QPS 下依 key 取值 | 毫秒 | DynamoDB、Cassandra、Bigtable、Redis | 掃描與彙總 |
| **搜尋** | 全文、篩選、facet | 10–100 毫秒 | Elasticsearch / OpenSearch | 唯一真實來源、join |

大多數真實設計會用到**兩到三種**：資料湖作為唯一真實來源，再加上符合服務模式的那一種儲存。
各家族的逐一比較在 [`./sql_vs_nosql.md`](./sql_vs_nosql.md)。

<!-- f06417cfb1d3 -->
### 3-3) 處理：批次、微批次、串流

**先依新鮮度需求選處理模式，再依團隊與平台選引擎 —— Spark、Flink 與資料倉儲內的 SQL 都能解決大多數問題。**

| 模式 | 新鮮度 | 常見引擎 | 優點 | 代價 |
|---|---|---|---|---|
| **批次** | 小時–天 | Spark、資料倉儲 SQL + dbt | 簡單、便宜、容易回補 | 資料舊 |
| **微批次** | 秒–分鐘 | Spark Structured Streaming | 沿用批次程式碼；吞吐量好 | 延遲下限 = 觸發間隔 |
| **串流** | 毫秒–秒 | Flink、Kafka Streams | 最低延遲，事件時間與狀態功能完整 | 狀態、watermark、維運較難 |
| **儲存內** | 與擷取一樣新 | materialized view、OLAP 擷取時 rollup | 不用跑作業 | 邏輯有限、綁廠商 |

引擎內部：[`./spark.md`](./spark.md)、[`./flink.md`](./flink.md)；什麼時候值得上串流：
[`./stream_pipeline.md`](./stream_pipeline.md#1-1-when-streaming-is-worth-it)。

<!-- 23aa6baf1e3c -->
### 3-4) 服務層：為讀者設計

**服務層由讀者的查詢、併發量與延遲決定 —— 管線應該剛好預先算出那個讀者需要的量，不多也不少。**

| 讀者 | 模式 | 從哪裡提供 |
|---|---|---|
| 分析師、臨時查詢 | 對歷史下任意 SQL | 資料倉儲 / lakehouse 的 gold 表 |
| 內部 dashboard | 固定切面、每幾分鐘更新 | 資料倉儲 + BI extract，或即時 OLAP |
| 面向使用者的分析（例如「你的貼文觀看數」） | 數千 QPS、以實體為單位、要新鮮 | 即時 OLAP 或預先算好的 KV |
| 產品功能（推薦、額度限制） | 單一 key、< 10 毫秒 | 由管線寫入的 KV / 快取 |
| ML 訓練 / 推論 | 時間點正確的歷史 / 最新值 | feature store：離線 + 線上（§6-5） |
| 其他系統 | 事件或檔案 | Kafka topic、reverse ETL、資料分享 |

取捨在於**預先計算 vs 查詢時計算**：預先計算讓讀取又快又便宜，但固定了你能問的切面；
直接查原始資料保留彈性，但每次查詢都要付錢。見 §5-5。

<!-- f3db713f6481 -->
### 3-5) 控制平面

**區分「一條管線」與「一個平台」的是控制平面：編排、附 lineage 的 catalog、schema registry、品質檢查與存取控制
—— 每個設計都要提到它，因為維運就住在這裡。**

| 元件 | 負責 | 例子 |
|---|---|---|
| **編排器** | 排程、相依關係、重試、回補 | Airflow、Dagster、Prefect |
| **Catalog + lineage** | 有哪些表、誰擁有、什麼餵給什麼 | Glue / Unity / Hive Metastore、DataHub、OpenLineage |
| **Schema registry** | 事件 schema 與其相容性規則 | Confluent / Glue Schema Registry |
| **品質** | 新鮮度、資料量、null、唯一性、對帳 | dbt tests、Great Expectations、Soda |
| **存取 / PII** | 誰能看哪個欄位、遮罩、刪除 | Lake Formation、Ranger、欄位標籤 |

## 4) 必懂的核心觀念 ⭐⭐⭐⭐⭐

<!-- 5d1aa7038938 -->
### 4-1) 傳遞語意與冪等性

**分散式管線預設是 at-least-once，所以正確性來自讓每一次寫入都冪等 ——
實務上的「exactly-once」指的是 at-least-once 傳遞加上冪等或交易式的 sink。**

| 語意 | 意思 | 成本 | 什麼時候用 |
|---|---|---|---|
| **At-most-once** | 可能遺失，絕不重複 | 最便宜 | 有缺口也無妨的指標 |
| **At-least-once** | 絕不遺失，可能重複 | 便宜 | 預設；搭配去重或 upsert |
| **Exactly-once（效果上）** | 每個事件只影響結果一次 | 交易、延遲、耦合 | 金流、要拿來計費的計數 |

冪等寫入的模式，依應該先考慮的順序：

1. **依邏輯日期覆寫分區** —— 重跑是取代，絕不是附加。
2. **以自然鍵做 upsert / `MERGE`** —— 重複的資料覆寫自己。
3. **在有界視窗內依生產端給的 `event_id` 去重**。
4. 以上都行不通時，才用**交易式 sink**（Kafka transaction、兩階段提交）。

### 4-2) 事件時間、遲到資料與會變動的結果

**依事件發生的時間彙總，而不是抵達的時間 —— 然後把「要等遲到事件多久、之後才到的怎麼處理」明確說出來。**

- **事件時間**才是業務口中「10:00 的點擊數」；處理時間只是你管線延遲的副產品。用處理時間重播會得到不同的答案。
- **Watermark** 表示「比 T 更早的事件大概都到了」；它用延遲換取完整度。
- 超過 watermark 才到的事件有三種處理方式：**丟掉並計數**、**更新結果**（以視窗為 key 做 upsert），
  或**送到 side output**，再由對帳批次修正。
- 對設計的影響：**結果是可修正的**，所以服務層的儲存必須接受以 `(dimension, window_start)` 為 key 的 upsert，
  使用者也必須接受昨天的數字可能會動。

機制：[`./stream_pipeline.md`](./stream_pipeline.md#3-time-semantics-and-watermarks-)。

<!-- 0c714aff1b4a -->
### 4-3) 分區、key 與資料傾斜

**依讀者來分區、依順序與平行度選 key，並在面試官問之前就先規劃熱點 key —— 因為真實流量從來不是均勻的。**

| 位置 | 依什麼分區 / 選 key | 理由 | 陷阱 |
|---|---|---|---|
| Kafka topic | 順序重要的那個實體（`user_id`、`order_id`） | 每個 key 內有序；消費端可平行 | 一個名人 key 塞爆一個 partition |
| 資料湖表 | 讀者會篩選的欄位，通常是事件日期 | 分區裁剪 | 切太細（每個使用者一個）→ 數百萬個小檔 |
| 串流作業 | 彙總用的 key | 狀態依 key 在本地 | key 傾斜 → 一個慢的 subtask 拖住 watermark |
| Spark 作業 | join / group 的 key | shuffle 時放在一起 | 一個 key 佔 40% 的列 → 一個 task 跑好幾小時 |

熱點 key 的解法：對 key **加鹽（salt）**再分兩階段彙總（`key#0..N` → `key`）、**把熱點 key 拆出來**另外處理、
在 shuffle 前**先在本地預彙總**，或把 join 的小表**廣播**出去。Spark 的傾斜：[`./spark.md`](./spark.md)；
串流的熱點 key：[`./stream_pipeline.md`](./stream_pipeline.md#8-3-hot-keys)。

<!-- 40be29b440bb -->
### 4-4) Schema、演進與資料契約

**生產端會在不通知你的情況下改 schema；設計必須讓不相容的變更在生產端大聲失敗，讓相容的變更不用部署就能流過。**

- 使用帶相容性模式的 **schema registry**：事件 topic 通常預設 **backward**（新的讀者能讀舊資料），所以消費端先升級。
- **安全的變更**：新增一個有預設值的選填欄位。**破壞性的變更**：改名、改型別、刪除必填欄位 —— 這些要以新欄位或新版 topic 來做。
- **資料湖表**：表格格式（Iceberg、Delta）以 ID 追蹤欄位演進，所以新增 / 改名只是中介資料的變更；絕不要依賴欄位位置。
- **資料契約**：由生產端團隊擁有 schema、語意與 SLA，並在 CI 中檢查；壞掉的紀錄送進 **dead-letter / 隔離**表，不進 silver。

Schema 規則的深入解析：[`./schema_design.md`](./schema_design.md)。

<!-- de168eec0b85 -->
### 4-5) 回補與重新處理是需求

**每條管線都會被重跑 —— 因為 bug、新欄位、遲到的來源 —— 所以第一天就要為回補而設計：確定性的作業、不可變的原始層，
以及以邏輯日期而非「現在」為 key 的輸出。**

- 作業讀取傳進來的**固定資料區間**，絕不用 `now()` 或「最新」，所以 `run(2026-10-01)` 今天跑和明年跑結果相同。
- **原始層不可變且長期保留**；所有衍生層都能刪掉再從它重建。
- **回補不影響今天**：用獨立的運算資源、限制併發、寫到影子表再切換，驗證通過後才發布到下游。
- 串流的情況：在保留期內**從 Kafka 重播**，超過保留期就從資料湖重播（Kappa 的答案）；新版作業並行執行，追上後再切換。

機制：[`./batch_pipeline.md`](./batch_pipeline.md#3-idempotency-determinism-and-backfills-)。

<!-- ecaa281b5600 -->
### 4-6) 資料品質與可觀測性

**一條跑起來全綠卻寫出錯誤數字的管線，是資料工程裡最糟的故障，所以設計要檢查的是資料，而不只是作業
—— 並讓關鍵的檢查擋住發布。**

| 檢查 | 抓到什麼 | 常見規則 |
|---|---|---|
| **新鮮度** | 卡住的來源或作業 | max(event_ts) 在 SLA 內 |
| **資料量** | 悄悄只載入一部分 | 列數落在上週同一天的 ±X% 內 |
| **Schema** | 上游的變更 | 契約 / registry 相容性 |
| **有效性** | 錯誤的值 | not null、範圍、允許值 |
| **唯一性** | 重試造成的重複 | 自然鍵唯一 |
| **對帳** | 邏輯 bug、資料遺失 | 總數與唯一真實來源相符 |

接著逐一決定每項檢查：**失敗**（擋住發布）、**警告**，或把壞資料**隔離**。
品質的深入解析：[`./batch_pipeline.md`](./batch_pipeline.md#6-data-quality-and-observability-)。

讓唯一真實來源只有一個，第二份寫入由它衍生。**

## 5) 取捨 ⭐⭐⭐⭐⭐

<!-- 22eee4c4bae2 -->
### 5-1) 批次 vs 串流

**預設用批次，只串流需求逼你串流的部分：串流換來新鮮度，代價是狀態、watermark、永遠在跑的運算與更難的維運。**

| | 批次 | 串流 |
|---|---|---|
| 新鮮度 | 小時 | 秒 |
| 正確性 | 輸入完整，容易推理 | 遲到資料、可修正的結果 |
| 成本 | 跑的時候才付錢 | 永遠在跑，依尖峰配置 |
| 回補 | 重跑某個日期 | 重播 log、新舊版本並行 |
| 維運 | 重試、一個 DAG | checkpoint、lag、狀態大小、擴縮 |

會翻轉成串流的情況：幾分鐘內就會失去價值的面向使用者或營運決策 —— 詐騙、告警、即時 dashboard、庫存。
「業務希望快一點」是先試每小時批次的理由。

<!-- 5b505839637f -->
### 5-2) Lambda vs Kappa

**Lambda 同時跑批次層與速度層再合併，要付兩套程式碼的代價；Kappa 只跑一套串流程式碼，靠重播 log 來重新處理
—— 在引擎與保留期允許時，Kappa 是現代的預設。**

多數公司實際採用的折衷：**一條串流路徑提供新鮮結果，加上每晚對資料湖跑一次批次對帳**，修正來得太晚的資料
—— 兩個作業，但批次那個只是簡單的 SQL，而不是第二份邏輯。深入解析：
[`./stream_pipeline.md`](./stream_pipeline.md#1-3-lambda-vs-kappa-architecture)。

<!-- 5d7aaf02d43a -->
### 5-3) 資料放在哪、在哪裡轉換

**ELT 進 lakehouse 或資料倉儲是現代的預設；取捨是成本與綁定 vs 簡單，而資料湖 vs 資料倉儲的界線，現在主要看還有誰要讀它。**

| 選擇 | 選 A 的時機 | 選 B 的時機 |
|---|---|---|
| **ETL vs ELT** | 轉換很重、PII 必須在載入前移除 | 資料倉儲運算可彈性擴展；保留原始資料以便重新處理（預設） |
| **Lake(house) vs 資料倉儲** | 多種引擎（Spark、Flink、ML）讀同一份資料；大量便宜儲存 | 主要是 SQL + BI；想要零維運的小團隊 |
| **開放表格格式 vs 專有格式** | 避免綁定、多引擎 | 單一廠商的功能與效能更重要 |

Lake vs warehouse vs lakehouse 的深入解析：[`./batch_pipeline.md`](./batch_pipeline.md#1-3-data-lake-vs-warehouse-vs-lakehouse)。

<!-- 19873f6baef2 -->
### 5-4) Exactly-once vs at-least-once 加冪等 sink

**優先選 at-least-once 傳遞進冪等的 sink：最終結果與 exactly-once 相同，延遲與耦合更少；
只有在附加型 sink 讓重複無法修正的地方，才付交易的代價。**

冪等 sink 只讓**重新輸出同一個結果**變得安全。它無法撤銷一筆已經被加進計數的重複**輸入**，
所以彙總在累加之前還需要其中一項：依 `event_id` 去重，或把彙總值放在引擎的 checkpoint 狀態裡
—— 重播時它會和來源 offset 一起回滾。

| | Exactly-once（交易式） | At-least-once + 冪等 |
|---|---|---|
| 延遲 | 在 checkpoint / commit 時輸出才可見 | 立即 |
| 耦合 | sink 必須支援交易 | sink 必須支援 upsert 或去重 |
| 故障時 | 交易中止、復原較久 | 短暫重複，被 key 覆寫 |
| 用於 | 別人當 log 消費的附加型輸出 | KV、OLAP upsert 表、`MERGE` 進資料湖 |

<!-- ec823df9beab -->
### 5-5) 預先計算 vs 查詢時計算

**常被問、切面固定的就預先計算；很少問或問法不可預期的，保留原始明細。**

| | 預先計算（rollup、物化表） | 查詢時（原始資料 + 快的引擎） |
|---|---|---|
| 讀取延遲 | 毫秒 | 秒 |
| 彈性 | 只有你 rollup 過的維度 | 任何切面 |
| 儲存 | 隨維度組合倍增 | 原始資料一份 |
| 變更 | 新維度 = 一次回補 | 一個新查詢 |

通常答案是兩者都要：**原始明細放資料湖，為 dashboard 與產品做幾個 rollup**，
並訂一條規則：某個查詢模式被證明是熱點時才新增 rollup。

<!-- 48612451eb62 -->
### 5-6) 擷取：CDC vs 查詢、push vs pull

**對資料庫來源，讀 log 的 CDC 是正確的預設 —— 它看得到刪除與每一次中間變更，又不會加重主庫負擔；
拿不到 log 時，才退回用查詢拉資料。**

| | 讀 log 的 CDC | 查詢式（`updated_at > :watermark`） |
|---|---|---|
| 硬刪除 | 抓得到 | 漏掉（需要定期全量比對） |
| 中間更新 | 全部 | 只有拉取當下的最新值 |
| 對來源的負擔 | 讀 log | 查詢資料表 |
| 建置 | replication slot / binlog 權限、connector 維運 | 一條 SQL |
| 風險 | 遺留的 slot 塞滿來源磁碟 | 時鐘偏差、同時間戳的列被漏掉 |

客戶端事件只能用 **push**（app 送到擷取 API → Kafka）；讓客戶端蓋上 `event_id` 與事件時間，
並預期會有重試、重複與時鐘偏差。

<!-- b64e4874ff33 -->
### 5-7) 新鮮度、正確性、成本 —— 明確選擇要換哪個

**你可以讓管線更新鮮、更正確或更便宜，而每一項都會犧牲其他項 —— 所以要說出這個設計偏向哪一項、為什麼。**

<!--CODE-->

範例句：*「計費偏向正確性，所以即使多花一小時也要對帳後才發布；即時 dashboard 偏向新鮮度，允許之後被修正。」*

<!-- e4c17f2963fa -->
### 5-8) 自建 vs 買現成

**無差異化的管線基礎設施 —— connector、Kafka、資料倉儲 —— 就買託管服務；你的資料或邏輯就是產品的地方才自建；
決定性的問題是：誰要為它 on-call。**

| 傾向託管的時機 | 傾向自管的時機 |
|---|---|
| 小團隊、標準的來源 | 規模大到託管費用成為最大成本 |
| 第一條管線上線的速度很重要 | 你需要服務沒有的功能或版本 |
| 法遵由廠商涵蓋 | 資料落地或網路規範不允許 |

### 6-1) 點擊流與產品分析

**題目**：「從我們的網頁與手機 app 收集事件，提供產品團隊 DAU、漏斗與留存，dashboard 要在 15 分鐘內更新。」

**釐清**：事件量（用 §2-2：每天 50 億）、哪些指標固定 vs 臨時查詢、手機事件會遲到多久（離線的手機：數小時到數天）、
事件裡有沒有 PII、保留需求。

<!--CODE-->

要說出口的決定：

1. **客戶端產生的 `event_id` 與事件時間** —— 手機重試與離線佇列讓重複和遲到成為常態，而不是例外。
2. **去重涵蓋得到的重試契約**：SDK 在 72 小時後放棄重送事件，collector 也拒收更舊的事件（會計數，不會默默丟掉），
   所以 72 小時的去重 TTL 看得到每一次重試。Pinot 以 `event_id` 做 upsert 是第二道防線：
   仍然漏過來的重複會覆寫自己那一列，而不是新增一列，所以即時數字本身就是對的，不必等批次路徑來修正。
3. **在 collector 做 schema 驗證**，搭配 dead-letter topic，讓一次壞掉的 SDK 發布不會污染 silver。
4. **兩條服務路徑**：Pinot 負責固定的新鮮 dashboard，資料湖 + 資料倉儲負責跨數月的臨時漏斗與留存分析。
5. **在批次裡做 sessionization**（30 分鐘無活動就切斷），這樣遲到事件也能被納入；只有產品需要即時 session 時才用串流 session window。
6. **DAU 是每天的相異使用者數**：批次裡算精確值，任意日期範圍的快速 rollup 用 HyperLogLog sketch（§6-4）。

追問：*事件晚 3 天才到* → 以事件日期分區並設重新處理視窗，最近 N 天的 dashboard 標示為暫定；
*GDPR 刪除* → 在資料落地的每一處依使用者刪除：資料湖表做列刪除，再**讓舊 snapshot 過期**，
time travel 才不會還留著那些列；衍生的資料倉儲表與 Pinot 也做同樣的刪除；Kafka 保留期短到讓資料自然過期；
備份的保留期要在法定期限內結束；並留下刪除紀錄，證明每一步都執行了。

### 6-2) 計費用的廣告點擊彙總

**題目**：「計算每個廣告每分鐘的點擊數；廣告主依此計費，也會在 dashboard 上看到。每天約 100 億次點擊。」

**釐清**：計費的正確性 vs dashboard 的新鮮度（兩種不同標準）、點擊詐騙 / 去重規則、點擊最晚會遲到多久、
查詢模式（依廣告、依活動、依分鐘）。

<!--CODE-->

要說出口的決定：

1. **兩個數字、兩種標準**：串流計數快但是*暫定*的；對不可變原始 log 的批次重算才是*計費*數字。
   串流裡做到 exactly-once 很好；讓帳單站得住腳的是對帳。
2. 計數前先**依 `click_id` 去重**（並套用詐騙過濾），被丟掉的點擊保留下來供稽核。
3. **以 `(ad_id, minute)` 為 key 做 upsert**，讓遲到的點擊修正那一分鐘，而不是新增一列。
4. **熱門廣告**：爆紅的廣告會塞爆單一 key —— 在每個 partition 先預彙總，或加鹽成 `ad_id#n` 再合併。
5. **以一分鐘為粒度彙總**，在儲存端 rollup 成小時與天；查某個活動是把分鐘加總，而不是掃點擊。

追問：*對帳發現 0.5% 的差異* → 計費以批次數字為準，發告警並調查（通常原因是超過允許遲到時間的點擊）；
*Flink 作業停了一小時* → 從 checkpoint 還原並從 Kafka offset 重播；dashboard 會過時，帳單不受影響。

### 6-3) Top-K 熱門排行

**題目**：「顯示過去一小時最熱門的前 100 個 hashtag（或歌曲、商品），每分鐘更新。」

**釐清**：精確或近似（近似幾乎都可以）、視窗（滑動 1 小時 vs 固定）、全球或分區域、
有多少不同的項目（數百萬）。

<!--CODE-->

要說出口的決定：

1. **兩階段彙總**：先依 key 平行計數，再由一個小的運算子只合併候選者 —— 絕不把每個事件都送到同一個節點。
2. **把滑動視窗拆成 60 個一分鐘的桶**：加上最新的桶、減掉最舊的桶，而不是每分鐘重算一整個小時。
3. **記憶體**：項目數百萬時，精確計數可能放不下。**每個一分鐘的桶各保留一個 Count-Min Sketch** ——
   用固定記憶體給出近似計數，只會高估。Sketch 無法列出裡面有哪些項目，所以每個桶也保留自己的
   **前 N 名候選清單**。每分鐘把 60 份清單取聯集作為這一小時的候選，再用 60 個仍有效的 sketch 重新評分；
   桶過期時，它的 sketch 和清單一起離開，所以沒有新事件的前段班會掉出排行，而不是一直卡在 heap 裡。
4. **「熱門趨勢」不等於「最受歡迎」**：要用相對基準的成長速度排名（這小時 vs 上週同一小時），否則排行永遠不會變。

### 6-4) 大規模相異計數（DAU、不重複訪客）

**題目**：「每頁每天的不重複訪客數，以及使用者任意挑選的日期範圍。」

**釐清**：精確或近似、哪些範圍（天、週、任意）、基數（數十億個訪客–頁面組合）。

**先說出口的答案**：**相異計數不能相加** —— 每日不重複數不能加總成每週不重複數 ——
所以要嘛保留原始 ID（精確、昂貴），要嘛每天保留一個**可合併的 sketch**，任何範圍就合併那些 sketch。

| 做法 | 精確？ | 儲存 | 範圍查詢 |
|---|---|---|---|
| 對原始事件 `COUNT(DISTINCT user_id)` | 是 | 所有事件 | 重掃整個範圍 |
| 每天一個 ID 集合 | 是 | 隨使用者數成長 | 集合聯集 —— 很重 |
| **每個 (page, day) 一個 HyperLogLog** | 約 0.8% 誤差 | 每個約 12 KB，固定 | 合併 sketch —— 很快 |
| 對密集整數 ID，每個 (page, day) 一個 bitmap（Roaring） | 是 | 對密集 ID 很精簡 | 把 bitmap 做 OR |

<!--CODE-->

追問：*財務需要精確值* → 對少數官方數字，每晚用批次從原始資料算精確值；所有互動查詢用 sketch。

### 6-5) 時間點正確的 feature store

**題目**：「ML 團隊在 notebook 和正式環境各算一次同樣的特徵，結果不一致。設計一個特徵平台。」

**釐清**：線上延遲（個位數毫秒？）、特徵的新鮮度（每日 vs 串流）、有多少模型與實體、訓練資料量。

<!--CODE-->

要說出口的決定：

1. **一份定義、兩個儲存**：同一份特徵程式碼同時寫入離線歷史與線上最新值，這就是消除 train/serve skew 的方法。
2. **時間點正確性**：時間 T 的訓練樣本只能看到在 T **當下或之前**算出的特徵值 —— 否則模型等於拿未來資料訓練（資料洩漏），
   離線表現很好，上線卻很差。
3. **線上儲存是 KV**，以實體為 key，並監控每個特徵的新鮮度。

### 6-6) 即時詐騙偵測

**題目**：「在每筆信用卡交易核准前為它打詐騙分數。」

**釐清**：延遲預算（核准路徑只容許數十毫秒）、規則 vs ML、哪些特徵需要歷史（速度類：每張卡過去 10 分鐘的交易數）、
評分服務掛掉時怎麼辦。

<!--CODE-->

要說出口的決定：

1. **決策是同步的，特徵是非同步的** —— 串流作業讓每張卡的彙總值一直保持在 KV 裡，所以評分只是一次查詢，而不是一次計算。
2. **Fail open 還是 fail closed** 是業務決定：評分逾時時，金額以下就核准，以上就拒絕或要求加強驗證。
3. **標籤要好幾週後才到**（chargeback），所以訓練時要以時間點正確的方式把特徵 join 到標籤（§6-5）。
4. **回饋迴圈**：被擋下的交易永遠拿不到標籤 —— 保留一小部分 holdout 或人工審查的樣本，模型才能繼續學。

<!-- 4a370f324b66 -->
### 6-7) 公司的資料平台（lakehouse）

**題目**：「我們有 200 個 Postgres 資料庫、Salesforce、事件串流，還有一堆亂七八糟的 cron 腳本。設計我們的資料平台。」

**釐清**：使用者（BI、ML、財務、產品）、團隊規模、雲端、法遵（PII、資料落地）、目前最痛的是什麼。

<!--CODE-->

要說出口的決定：

1. **一種開放表格格式、一個 catalog**，讓每個引擎都讀同樣的表 —— 不需要每個工具各存一份。
2. **有明確擁有者的 medallion 分層**：平台團隊擁有 bronze，各領域團隊擁有自己的 gold mart（輕量的 data mesh 模型），
   用契約守住邊界。
3. **有護欄的自助服務**：新來源與新 mart 都有範本，這樣 200 個資料庫就不會變成 200 條各自客製的管線。
4. **預設就有治理**：擷取時就標記 PII，在 silver 遮罩，依 key 傳遞刪除。
5. **分階段進行**：先處理最痛的使用者（通常是財務報表），再逐一遷移 cron 腳本，每一個都要與舊輸出對帳。

<!-- 77a4a257ab96 -->
### 6-8) 把地端 Hadoop 遷移到雲端

**題目**：「在不影響業務的情況下，把 2 PB 的 HDFS、3,000 個 Hive / Spark 作業與它們的使用者搬到雲端。」

**要說出口的決定**：

1. **先盤點與 lineage**：哪些作業餵給哪些使用者；很多作業最後會發現已經沒人用了。
2. **先儲存、後運算**：把資料複製到物件儲存（大量傳輸 + 增量同步），註冊到 catalog，再把新的運算指向它。
3. **依面向使用者的領域遷移，而不是依作業**，並且每個領域都**雙軌執行**：新舊管線並行，自動比對輸出，連續 N 天一致才切換。
4. **先換平台，再最佳化**：先把 Spark/Hive SQL 原封不動搬到託管 Spark；轉換成表格格式、調整分區與檔案大小，
   都在切換之後做，不要在切換期間做。
5. **每個領域都有回滾計畫**，並凍結舊系統上的新功能。

追問：*HDFS 小檔* → 在複製時順便 compaction；*Hive 的 `INSERT OVERWRITE` 語意在物件儲存上* → 表格格式讓覆寫是原子的，
單純的 S3 目錄做不到。Hadoop 這一側的深入解析：[`./hadoop.md`](./hadoop.md)。

## 7) 故障模式與維運 ⭐⭐⭐⭐

<!-- 27e2c3d2f44f -->
### 7-1) 會壞在哪裡，以及設計上的對策

**在面試官提出之前先點出故障，並給出設計對它的答案 —— 這是這一關最可靠的資深訊號。**

| 故障 | 症狀 | 設計對策 |
|---|---|---|
| 上游 schema 變更 | 作業失敗，更糟的是 null 一路流下去 | registry 相容性、CI 中的契約、隔離 |
| 重複事件（重試、重播） | 計數灌水 | `event_id` 去重、冪等的 upsert / 覆寫 |
| 遲到或亂序的資料 | 昨天的數字會動 | 事件時間、watermark、重新處理視窗、對帳 |
| 熱點 key / 傾斜 | 某個 task 或 partition 落後 | 加鹽、兩階段彙總、拆出那個 key |
| 只載入一部分 | 某天只有 60% 的列，作業卻是綠的 | 資料量檢查擋住發布 |
| 串流作業當掉 | lag 增加、dashboard 過時 | checkpoint、從 offset 重啟、lag 告警 |
| 擷取壓垮來源資料庫 | 正式環境事故 | 從 replica / log 做 CDC、限速 |
| 小檔 | 查詢變慢、請求費用變高 | compaction、目標檔案大小、較粗的分區 |
| 壞掉的部署寫入錯誤資料 | 下游數字錯誤 | 原始層 + 回補、用 time travel 回滾、影子執行 |
| 成本失控 | 帳單翻倍 | 分區裁剪、生命週期 / TTL、依團隊歸屬成本 |

<!-- 7313fade9df1 -->
### 7-2) SLA 與要監控什麼

**從使用者的角度定義 SLA ——「財務 mart 在 06:00 前完整且正確」—— 並針對它監控資料，而不只是監控作業。**

| 層 | 監控 | 何時告警 |
|---|---|---|
| 擷取 | consumer lag、connector 狀態、DLQ 比例 | lag > 新鮮度預算；DLQ 暴增 |
| 串流作業 | checkpoint 時間 / 失敗、watermark 延遲、backpressure | checkpoint 失敗；watermark 停滯 |
| 批次作業 | 執行時間對比歷史、重試、預測是否會錯過 SLA | 以目前速度會錯過截止時間 |
| 資料 | 新鮮度、資料量、null、唯一性、對帳 | 任何阻擋型檢查失敗 |
| 成本 | 每條管線 / 每個團隊的花費、掃描的位元組 | 超過預算或趨勢異常 |

維運手冊：[`./batch_pipeline.md`](./batch_pipeline.md#9-failure-handling-and-reruns-)
與 [`./stream_pipeline.md`](./stream_pipeline.md#12-operations-)。

## 8) 資深訊號與地雷 ⭐⭐⭐⭐

<!-- c68f8cd5105c -->
### 8-1) 資深的回答聽起來像什麼

**資深的回答少談工具、多談為什麼：說出每個選擇服務的需求、它拒絕了哪個方案，以及什麼會讓它改變主意。**

- *「我會先從每小時批次開始；如果 15 分鐘的 SLA 是硬性的，我只把 dashboard 那條路徑改成串流，其餘維持批次。」*
- *「傳遞是 at-least-once，所以 sink 是對 `(ad_id, minute)` 的 upsert —— 重複的資料會覆寫自己。」*
- *「原始資料不可變，所以邏輯 bug 只是一次回補，不是資料遺失。」*
- *「計費讀的是對帳過的批次數字；串流的那個標示為暫定。」*
- *「如果一個 key 佔了 30% 的流量，我會對它加鹽，再在第二階段合併。」*
- *「上線後我會盯的是 watermark 延遲，因為那就是讓 dashboard 悄悄過時的原因。」*

<!-- d47da5ff12de -->
### 8-2) 讓這一關沉船的地雷

- ❌ 還沒問新鮮度、資料量與使用者就開始畫架構。
- ❌ 因為聽起來很現代就把所有東西都串流化，卻沒有任何需求需要它。
- ❌ 假設事件只到一次、依序、準時。
- ❌ 對「這要怎麼回補？」或「這個作業跑了兩次會怎樣？」沒有答案。
- ❌ 所有讀者共用一種儲存 —— 拿資料倉儲去撐每秒 1 萬次的產品 API，或把 Kafka 當長期封存。
- ❌ 估算從沒變成分區數、叢集大小或成本。
- ❌ 直到面試官提起才想到資料品質、PII 與刪除。
- ❌ 列出一堆工具，卻沒說每個是拿來做什麼的。

## 9) 考前檢查清單

每個觀念一行 —— 如果每一行你都能說出口，這一關就涵蓋到了。

- **規劃** —— 釐清（新鮮度、資料量、使用者、正確性）→ 估算 → 分層 → 深入正確性 → 故障 + 擴展 → 取捨
- **數字** —— 一天 10⁵ 秒、尖峰 2–5 倍、每事件約 1 KB、Parquet 約 5 倍、partition 數 = 尖峰 MB/s ÷ 約 5–10 MB/s
- **架構** —— 來源 → 擷取 → 不可變的 raw → silver → gold → 每種讀者各自的服務儲存，控制平面橫跨各層
- **正確性** —— at-least-once + 冪等 sink、`event_id` 去重、事件時間 + watermark、以 key 存放可修正的結果
- **回補** —— 固定區間上的確定性作業、依邏輯日期覆寫、從 raw 重播
- **一致性** —— CDC 或 outbox，絕不雙寫
- **取捨** —— 批次 vs 串流、Lambda vs Kappa、ELT + lakehouse、預先計算 vs 查詢時計算、CDC vs 查詢拉取、新鮮度 / 正確性 / 成本
- **經典題** —— 點擊流、計費用廣告點擊（串流暫定 + 批次對帳）、top-K（兩階段 + Count-Min）、相異計數（HLL 合併）、feature store（時間點正確）、詐騙（同步評分 + 非同步特徵）、平台、遷移（雙軌執行）
- **維運** —— 以資料為準的 SLA、lag / watermark / checkpoint / 新鮮度 / 資料量告警、隔離、依團隊歸屬成本
