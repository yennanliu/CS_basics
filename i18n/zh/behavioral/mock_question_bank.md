# 行為面試模擬題庫

> **範圍** — 二十五道經典行為面試題，供模擬練習使用。每題都附上入門級（L3／應屆畢業生）的完整範例回答、面試官可能的追問，以及這個回答為什麼得分。評分標準、回答模式與故事庫的建立方法放在兩份公司指南裡；這份文件是練習題組。
> **另見**：[googleyness.md](./googleyness.md) — Google 這一輪評什麼，以及「釐清 → 選項 → 決定 → 追蹤」的回答模式；[amazon_leadership_principles.md](./amazon_leadership_principles.md) — 每道題對應的十六條原則。

<!-- 345915dcf93e -->
## 1. 如何進行一場模擬面試

1. **挑三到五題**，從下方索引中選，並混合不同主題。真實的一輪面試會在 45 分鐘內問四到六題。
2. **請夥伴把題目唸出來**，或自己唸完後開始計時。先不要看範例回答。
3. **用兩到三分鐘回答**，講你自己的故事。超過三分鐘，代表情境講太長了。
4. **接受追問。** 夥伴從該題的追問清單中挑兩題，並一直問「為什麼？」，直到故事講不出更多細節。
5. **評分**，用下面的表格；然後再讀範例回答，記下一件它做到、而你沒做到的事。

| 評等 | 回答展現了什麼 |
|---|---|
| **強** | 第一人稱、具體行動、你權衡過的取捨、結果有數字、教訓之後有再用上 |
| **可接受** | 故事清楚，但行動單薄，或結果只是「進行得很順利」 |
| **弱** | 大多是「我們」、用假設性的回答回應過往行為題，或沒有反思 |

> **重點** — 範例回答示範的是*結構*，不是要你背下來的故事。面試官會追問只有親身經歷才會知道的細節，所以借來的故事在第二個「為什麼？」就會垮掉。

## 3. 開場題

大多數面試以這幾題開場。它們不太針對某項特質評分，而是建立面試官的第一印象，並給他們可以追問的話題。

<!-- 6149039318d0 -->
### Q1. 請介紹你自己

**考察** — Google：動機 · Amazon：不直接對應；它為後面的題目埋下話題

**範例回答**

> 我是資訊工程系大四學生。我做過的東西大多在後端：去年暑假我在一個支付團隊實習，把一份對帳報表從每晚批次改成每小時執行，讓財務等數字的時間從一天縮短到一小時。在那之前，我當了兩學期資料結構課的助教，在那裡學會用三種不同方式解釋同一個概念，直到對方聽懂為止。課外我參與一個開源的 Python linter，有六個 pull request 被合併，大多是新的規則和它們的測試。接下來我想找一個團隊，能做很多人依賴的系統，並且固定得到比我更強的工程師的 code review。

**要演練的追問**

- 對帳報表那次修改，最難的部分是什麼？
- 為什麼選後端而不是前端？
- 當助教讓你寫程式的方式有什麼改變？

**為什麼得分** — 九十秒內講完，現在 → 過去 → 未來，每一句都是面試官可以接著追問的鉤子。講的是成果，不是職稱。

### Q2. 為什麼想來這間公司？

**考察** — Google：動機 · Amazon：Customer Obsession

**範例回答**

> 兩個理由，都和工作本身有關。第一是規模：實習時我最喜歡的問題，是那些因為要跑幾百萬次、所以小小的低效率也很重要的問題，而在這裡那是常態而不是例外。第二是我從外面看到的工程文化——設計文件、每個變更都有 code review，以及不究責地寫事故報告的習慣。我讀過去年一次儲存系統中斷的公開事後檢討，那是我第一次看到一個團隊把失敗解釋得那麼坦白。我想在職涯早期就在這樣的環境裡學習，而我習慣為自己的修改寫測試和文件，應該很適合這裡。

**要演練的追問**

- 你最想加入哪個團隊或產品？為什麼？
- 什麼情況會讓你一年後離開？
- 關於我們怎麼開發軟體，有什麼是你知道而大多數候選人不知道的？

**為什麼得分** — 理由具體、和工作相關，並連結到候選人已經做過的事。完全沒提福利、名聲或品牌。

### Q3. 請說說一個讓你自豪的專案

**考察** — Google：動機 · Amazon：Deliver Results、Ownership

**範例回答**

> **Situation（情境）** — 在作業系統課上，三人一組要做一個小型檔案系統。大多數組別通過測試就停了。
>
> **Task（任務）** — 我負責區塊配置器和當機復原路徑，這是大多數組別略過的部分，因為測試幾乎沒涵蓋到。
>
> **Action（行動）** — 我寫了一個測試工具，在寫入過程中的隨機時間點砍掉程序，再檢查磁碟映像是否一致。第一次執行時，200 次試驗中有 14 次映像損毀。我追查到原因是先寫 inode 再寫資料區塊，於是調換寫入順序，並為 metadata 加了一個簡單的日誌（journal）。每次修改後我都重跑測試工具，並在 README 裡維護一張失敗次數表，讓隊友看得到趨勢。
>
> **Result（結果）** — 最終版本通過了全部 1,000 次試驗。教授把我們的測試工具當作下一屆課程的參考。我自豪是因為沒人要求我做：成績不取決於它，而且那是我第一次針對失敗而不是針對功能做測試。

**要演練的追問**

- 為什麼先寫 inode 會讓映像損毀？
- 現在重做的話，你會做什麼不同的事？
- 你和兩位隊友怎麼分工？

**為什麼得分** — 展現了超越成績的當責、可量測的前後對比，以及面試官可以深挖的技術深度。候選人也說出*為什麼*自豪，那才是這題真正在問的。

### Q4. 請說說你曾經和主管意見不合的經驗

**考察** — Google：挑戰現狀 · Amazon：Have Backbone; Disagree and Commit

**範例回答**

> **Situation（情境）** — 實習時，主管要我的專案（一個內部管理頁面）加一個 CSV 匯出按鈕，把資料表的每一列都拉出來。
>
> **Task（任務）** — 這個功能由我開發，而我認為資料表變大後，拉出所有資料列會逾時。
>
> **Action（行動）** — 我沒有空泛地爭論，而是去量測。我把一份正式環境資料的副本載入 staging，測量查詢時間：目前 200 萬列要 40 秒，而請求上限是 30 秒。我在一對一會議中帶著數字和兩個選項：分頁匯出，或用背景工作把檔案寄出。主管點出一件我沒想到的事——使用者只需要最近 30 天的資料。所以我們決定做依日期篩選的匯出，比我的兩個選項都簡單。
>
> **Result（結果）** — 一週內上線，回應時間在兩秒以內。我學到在意見分歧時，要同時帶著資料*和*一個開放的問題；主管有我不知道的脈絡，最好的答案來自兩者的結合。

**要演練的追問**

- 如果主管說「照原樣上線」，你會怎麼做？
- 你怎麼提出來，又不讓它聽起來像是在拒絕？
- 有什麼是你判斷錯的嗎？

**為什麼得分** — 異議有量測數據支持，提出時帶著選項而不是直接否決，而且候選人把更好的點子歸功於主管。這是有骨氣但不自負。

### Q5. 請說說你曾經和難相處的人共事的經驗

**考察** — Google：協作 · Amazon：Earn Trust

**範例回答**

> **Situation（情境）** — 在一門為期一學期的軟體工程專題中，有位隊友會拒絕我們大多數人開的 pull request，常常只留一句「我不會這樣寫」。
>
> **Task（任務）** — 我是開最多 pull request 的人，而我們的速度已經掉到一週只合併兩個變更。
>
> **Action（行動）** — 我沒有在 review 討論串裡回覆，而是約他喝咖啡。原來他在之前的課上曾因為建置壞掉被責怪，很怕再發生一次。我提議把他在意的標準寫下來——每個新函式都要有測試、handler 不能直接呼叫資料庫——做成 repo 裡的一份簡短檢查清單，並加一個在每個 pull request 上跑測試的 CI 工作。我也請他在下一個功能和我結對程式設計，讓他看到我的工作方式。
>
> **Result（結果）** — review 意見從「我不會這樣寫」變成對照清單的具體評論，下一週我們合併了九個變更。他成了我們最有幫助的審查者。我學到「難相處」的行為通常有原因，當面問清楚比在留言裡對抗快得多。

**要演練的追問**

- 如果喝咖啡沒用，你會怎麼做？
- 你有找老師或其他人介入嗎？
- 你自己的 pull request 需要改變什麼？

**為什麼得分** — 候選人先找對方的理由，把個人摩擦轉成共同的流程，並交代了之後的關係。對方不是故事裡的反派。

<!-- f30279a1ead1 -->
### Q6. 請說說你曾經遇到隊友沒有盡到本分的經驗

**考察** — Google：協作 · Amazon：Ownership、Earn Trust

**範例回答**

> **Situation（情境）** — 在一個為期四週、類似黑客松的課程專案中，我們四人裡有一位到第二週結束都還沒推過任何程式碼。
>
> **Task（任務）** — 我負責協調看板，而他負責的通知服務卡住了我們的展示。
>
> **Action（行動）** — 我私下傳訊息給他，而不是在站立會議上提出來。他說他每週要打工二十小時，低估了這個任務。我們重新分工：他保留電子郵件範本，可以用零碎時間完成；我接手需要長時間專注的佇列邏輯。我更新了看板讓團隊看到新的分工，但沒有向大家解釋他的個人狀況。我也把我們的進度確認改到晚上，配合他有空的時間。
>
> **Result（結果）** — 服務在展示前三天完成，並由他上台展示。我學到在假設是不夠努力之前，先問是什麼擋住了對方，然後修正計畫而不是修理人。

**要演練的追問**

- 到什麼程度你會去找老師？
- 你多承擔工作，其他隊友有什麼感覺？
- 如果他完全沒回應，你會怎麼做？

**為什麼得分** — 先私下再公開、具體的重新規劃、對隊友狀況保持謹慎，並且對結果負責而不是追究責任。

## 5. 失敗、錯誤與回饋

<!-- c24ec88716ae -->
### Q7. 請說說你曾經失敗的經驗

**考察** — Google：回饋與成長 · Amazon：Learn and Be Curious、Earn Trust

**範例回答**

> **Situation（情境）** — 大二時，我帶一個三人小組參加校內 app 競賽，做一個讀書會配對 app。
>
> **Task（任務）** — 範圍和時程是我定的，所以計畫是我的。
>
> **Action（行動）** — 我規劃了八個功能，結果八週中的前五週，我們把每個功能都做到一半。直到第六週，我都沒請任何一位學生試用過。等到我們終於測試時，五位受試學生只在乎一件事——找到同一個課程班級的人——而那個功能是完成度最低的。
>
> **Result（結果）** — 我們沒有進前十名，評審的回饋和學生的一樣：做太多，沒有一個做完。我改變的是：之後的每個專案，我都在第二週結束前把東西放到使用者面前，並把範圍砍到他們會用的部分。實習時，我在第六天就把第一版管理頁面展示給兩位使用者，其中一則意見讓整個畫面從計畫中刪掉。

**要演練的追問**

- 為什麼沒有更早找使用者測試？
- 隊友對結果有什麼反應？
- 回頭看，你會砍掉什麼？

**為什麼得分** — 真實的失敗、真實的代價，由候選人承擔而不是怪環境，還有之後的例子證明教訓有內化。它不是包裝過的優點。

<!-- 8057fea3f0b5 -->
### Q8. 請說說一個影響到其他人的錯誤

**考察** — Google：做對的事 · Amazon：Earn Trust、Ownership

**範例回答**

> **Situation（情境）** — 實習時，我寫了一個資料庫 migration，新增一個帶預設值的欄位。
>
> **Task（任務）** — 這個變更是我的，而且已經通過 code review。
>
> **Action（行動）** — 它在 staging 執行時鎖住資料表四分鐘，另一個團隊的整合測試在那段時間內失敗了。我看到他們的頻道一片紅，發現時間和我的 migration 吻合。十分鐘內我就在他們的頻道發文：我跑了什麼、什麼時候跑的，以及這就是原因。我先回滾，再把它改寫成三個步驟——先新增不帶預設值的欄位、分批回填資料、最後才設定預設值——並請團隊的資料庫專家審查。我也在 migration 檢查清單裡加了一行，關於大型資料表上的預設值。
>
> **Result（結果）** — 改寫後的 migration 在正式環境執行時沒有鎖表。另一個團隊感謝我在他們花時間除錯前就告訴他們。我學到快速承認錯誤，對所有人來說都比爭論是誰的錯成本更低。

**要演練的追問**

- 為什麼 code review 沒抓到？
- 在別的團隊頻道發文，你有什麼感覺？
- 檢查清單上那一行寫了什麼？

**為什麼得分** — 快速而具體的揭露、修正加上防止重演的機制，而且沒有把責任推給核准的審查者。

<!-- 2d8b2ae2d9c7 -->
### Q9. 請說說你收過最嚴厲的回饋

**考察** — Google：重視回饋 · Amazon：Earn Trust、Learn and Be Curious

**範例回答**

> **Situation（情境）** — 實習進行到一半時，我的 mentor 說我的 pull request 很難審：平均大約 600 行，而且把重構和新行為混在一起。
>

- 為什麼先加臨時說明，而不是等修正？
- 如果開發者拒絕，你會怎麼做？

**為什麼得分** — 說得出使用者是誰，用候選人手上已有的資料量化問題，現在給使用者權宜之計、之後有正式修正，而且超出職責但沒有越權。

### Q21. 請說說你曾經必須在準時上線和把事做對之間抉擇的經驗

**考察** — Google：做對的事 · Amazon：Insist on the Highest Standards、Earn Trust

**範例回答**

> **Situation（情境）** — 一個內部工具上線的前一天，我發現只要拿掉某個查詢參數，它的匯出端點就會回傳所有團隊的資料，而不只是使用者自己團隊的。
>
> **Task（任務）** — 那個端點不是我寫的，也沒有其他人注意到，而上線消息已經公告給 200 位使用者。
>
> **Action（行動）** — 我重現了兩次確認無誤，然後在一小時內同時告訴主管和端點的作者，附上能顯示資料外洩的確切請求。我沒有把它貼到公開頻道。我提出兩個選項：延後一天上線，或上線時先停用匯出按鈕。作者當天下午就修好了權限檢查，我寫了一個不帶該參數發送請求的測試。我們先停用匯出上線，隔天早上測試通過後再開啟。
>
> **Result（結果）** — 工具準時上線，沒有任何資料外洩。主管請我把這個測試加進團隊每個新端點的審查清單。我學到安靜而快速地提出問題、並帶著解法，能讓大家很容易做對的事。

**要演練的追問**

- 為什麼不自己修？
- 為什麼不告訴整個團隊？
- 如果主管說照原樣上線呢？

**為什麼得分** — 及早向對的人提出令人不舒服的事實，附上重現方式和選項。結果同時保護了使用者和上線時程，候選人也把修正歸功於作者。

## 9. 領導與培養他人

<!-- 3eea53a41276 -->
### Q22. 請說說你曾經在不是負責人的情況下帶領團隊的經驗

**考察** — Google：自發型領導 · Amazon：Earn Trust、Ownership

**範例回答**

> **Situation（情境）** — 我們五人的畢業專題小組有一位名義上的組長，技術很強但很少主持會議；三週後我們還沒有共同的計畫，兩個人做出了重複的登入頁面。
>
> **Task（任務）** — 我不是組長，也不想削弱他的角色。
>
> **Action（行動）** — 我先找他談，提議由我主持一場規劃會議，由他報告架構。他同意了。會議中我請每個人列出自己正在做的事，放到同一個看板上，結果找到重複的部分，以及兩個沒有人負責的功能。我建議每週兩次、每次十五分鐘的站立會議，自願主持前兩次，之後輪流主持。
>
> **Result（結果）** — 我們砍掉重複的工作，在期限前一週完成所有規劃的功能，第一個月之後組長就自己主持站立會議了。我學到沒有職權的領導，往往是把舞台讓給別人，同時補上他們留下的空缺。

**要演練的追問**

- 為什麼先去找組長？
- 有人抗拒站立會議時你怎麼做？
- 如果組長拒絕，你會怎麼做？

**為什麼得分** — 領導是補上缺口，在正式負責人的支持下進行而不是繞過他，最後再交還出去。這正是 L3 標準要求的自發型領導訊號。

### Q23. 請說說你曾經幫助別人成功的經驗

**考察** — Google：自發型領導、協作 · Amazon：Hire and Develop the Best

**範例回答**

> **Situation（情境）** — 實習時，一位新實習生在我之後三週加入，被分派到一個 bug，出在我剛學會的那部分程式碼。
>
> **Task（任務）** — 我不是她的 mentor，但我熟悉那段程式碼，而她的 mentor 那週在休假。
>
> **Action（行動）** — 她報到第一天下午，我主動撥出一小時。我沒有直接告訴她怎麼修，而是帶她走一遍我會怎麼找：log 在哪裡、怎麼在本機執行服務、我怎麼追蹤請求的路徑。然後我讓她自己操作、我在旁邊看，只有在她卡住超過十分鐘時才介入。我也分享了我為自己寫的程式碼筆記。
>
> **Result（結果）** — 她兩天內自己修好了 bug，並在那週開出她的第一個 pull request。兩週後，她用同一份筆記回答下一位實習生的問題。我學到教人怎麼找答案，比直接給答案影響得更遠。

**要演練的追問**

- 你怎麼和自己的工作取得平衡？
- 當對方只想要答案、不想要方法時，你怎麼做？
- 你怎麼知道是你的幫忙造成了差別？

**為什麼得分** — 沒人要求就主動幫忙、有意識的教學方式，以及幫助產生倍增效果的證據。功勞留給真正做事的人。

## 10. 假設情境題

Google 比 Amazon 更常問這類題目。使用 Google 指南中的模式：釐清、選項、決定、追蹤——如果有真實故事，最後再用它來佐證。

<!-- 65d7e1d43f19 -->
### Q24. 如果主管要你上線一個你認為還沒準備好的東西，你會怎麼做？

**考察** — Google：做對的事 · Amazon：Have Backbone; Disagree and Commit

**範例回答**

> **Clarify（釐清）** — 我會先問在這個情況下「還沒準備好」是什麼意思，因為答案會因此不同。它是對使用者的風險——資料遺失、資安、核心流程壞掉——還是品質上的落差，例如細節不夠精緻或測試覆蓋不足？還有，推動這個日期的是什麼：對客戶的承諾，還是內部目標？
>
> **Options（選項）** — 如果是對使用者的風險，我會帶著證據直說，並提出能安全趕上日期的做法：用 feature flag 先開放給一小群人、砍掉有風險的部分，或延後幾天。如果是品質落差，我會記錄下來，開好後續工作並指派負責人，然後上線。
>
> **Decide（決定）** — 決定權在主管，但他們應該在掌握事實的情況下做決定。我會用兩三句話把風險寫下來，目的是讓事情清楚，而不是保護自己。
>
> **Follow through（追蹤）** — 如果我們上線，我就全力投入：上線後盯著指標和錯誤，並第一個回應。實習時我曾在上線前一天提出一個資料外洩的 bug；我們停用匯出功能準時上線，隔天再開啟。

**要演練的追問**

- 如果主管還是說要上線，而你認為使用者會受到傷害呢？
- 你怎麼表達反對又不傷害關係？
- 什麼時候你會越過主管往上呈報？

**為什麼得分** — 它把風險和個人偏好分開，提出尊重日期的選項，決定後全力投入，最後以真實故事作結。要準備第一個追問：你會在哪裡劃下往上呈報的界線，也是答案的一部分。

### Q25. 如果兩位資深工程師給你互相衝突的指示，你會怎麼做？

**考察** — Google：在模糊中前進、協作 · Amazon：Earn Trust

**範例回答**

> **Clarify（釐清）** — 我會先確認自己正確理解了兩人的意思，因為衝突常常出在我的轉述，而不是他們的本意。我也會問誰擁有這個決定權——技術主管、我的主管，還是他們其中一位。
>
> **Options（選項）** — 我可以自己挑一個方向、分別回去找兩人，或把兩種觀點並列、請他們一起決定。自己挑一個有之後白做的風險；分別去找往往只會重演衝突。
>
> **Decide（決定）** — 我會寫一份簡短的說明，列出兩種做法、我理解的各自取捨，以及我傾向哪一個和原因，在同一個討論串裡寄給兩人，並副本給有決定權的人。這讓分歧變成關於做法本身，而不是我聽哪位資深工程師的。
>
> **Follow through（追蹤）** — 在他們決定的期間，我會先做兩種做法共通的部分，這樣我不會被卡住。決定之後，我會把它記在設計文件裡，避免再被翻案。實習時我遇過類似的情況，是關於命名慣例，一份五行的比較在一則回覆內就解決了。

**要演練的追問**

- 如果他們還是無法達成共識呢？
- 如果有決定權的人選了你認為比較差的選項呢？
- 你怎麼避免看起來像在選邊站？

**為什麼得分** — 它把衝突當成資訊問題處理，把它交給決策者，等待期間候選人保持產出，並把決定記錄下來。

## 11. 模擬面試之後

- **數一數「我們」。** 任何一個「我們」比「我」多的回答，都要重寫行動那一段。
- **找出數字。** 每個結果都應該有一個：節省的時間、錯誤率、使用者數、成績、天數。
- **檢查教訓。** 每個故事都應該以你改變了什麼、以及之後某次用上它作結。
- **對應你的故事。** 回答完全部 25 題後，你總共應該用了六到十個故事。如果一個故事回答了超過四題，面試會察覺；如果有題目沒有故事可講，那就是要補的缺口。
- **一週後重練表現弱的題目**，換一位夥伴，因為熟悉的聽眾會不再問難的追問。
